### 計時預算量測

條件：6,000 筆虛構景點（`pnpm check:scale --keep`，種子 20261018），`scripts/scale/perf.mjs`，視窗 390px、4 倍 CPU 降速、Slow 4G（延遲 562.5 ms、下載 1.44 Mbps）、停用快取，靜態伺服器以 brotli（品質 4）回應文字檔；Playwright Chromium，每項 3 次取中位數；機器為 MacBook Air M4。

| 預算 | 上限 | 量測（中位數） | 結果 |
| --- | --- | --- | --- |
| 無條件列表 FCP（`/`） | ≤ 1.5 s | 1.25 s（樣本 1.22–1.27 s） | 通過 |
| 列表 HTML brotli（`/`） | ≤ 30 KB | 4.1 KB（品質 11，原始 20.9 KB；`/page/2/` 3.7 KB） | 通過 |
| 手機隱藏的圖片 | 不下載 | 首頁介紹插畫（手機隱藏）未被請求，只載入 1 張列表縮圖 | 通過 |
| 帶篩選條件進站到畫出結果（`/?county=臺南市`） | ≤ 4 s | 3.48 s | 通過 |

| 第一次文字搜尋 Pagefind 傳輸，廣查詢「公園」 | ≤ 300 KB | 187 KB／7 個請求 | 通過 |

註記：

- 所有預算通過。Carl 於 2026-10-17 決定「進站 ≤ 4 s」只適用篩選條件；帶文字查詢進站只記錄秒數，傳輸量仍受「第一次文字搜尋 ≤ 300 KB」約束。沒有拆分列表 JSON 或另開票。帶篩選條件（縣市）進站為 3.48 s，通過；無條件 `/?page=2` 直接導向 `/page/2/`，不下載列表 JSON 與 Pagefind。
- 文字查詢進站超過 4 s 的瓶頸是 Pagefind 自己的相依請求鏈，不是頻寬：HTML → `pagefind.js` → `pagefind-worker.js` → `pagefind-entry.json` → `.pf_meta` 與 wasm → 索引片段，每一步都要等上一步回應才發得出去，在 Slow 4G 的 562.5 ms 延遲下一步約 0.6–0.9 s，加上 wasm 與 meta 約 100 KB 的傳輸（約 0.6 s），下限約 5 s。列表 JSON（量測伺服器以 brotli 品質 4 壓縮約 186 KB）與景點對照表（47 KB）和這條鏈平行，只多拖慢約 0.2 s，不是主因。
- 已做的優化：帶 `query` 進站時，首頁（`/`）的內嵌小段程式在 HTML 解析完就先起跑 Pagefind（`import` 加 `init()`）、景點對照表與列表 JSON（`<link rel="preload">`），不等主程式與其共用 chunk 下載，起跑點從 1.88 s 提前到 1.23 s；搜尋框聚焦時（`warm()`）除了列表 JSON 也預載並 `init()` Pagefind 與對照表（US36）。傳輸量不變：Pagefind 187 KB／7 個請求（廣查詢）、271 KB／11 個請求（窄查詢），仍 ≤ 300 KB，列表 JSON 沒有重複下載。
- 曾考慮但未採用的縮短方式：換掉 Pagefind 的 worker 路徑（少一步，約 −0.7 s，但 `noWorker` 不是文件化選項）、文字搜尋改用列表 JSON 在瀏覽器端自行比對（沒有索引鏈，但搜尋範圍與排序不同於 Pagefind）。
- 資料是虛構且稀疏的：多數景點沒有年齡、親子條件與插畫，摘要很短，所以列表 JSON 只有約 1 MB。真實景點的欄位更滿，列表 JSON 會比這裡大；視實際內容用 `pnpm check:output` 的 1.5 MB／400 KB 上限盯住，接近時再考慮拆檔。
- Pagefind 傳輸由伺服器端累計壓縮後本文，Web Worker 的請求不經過頁面 CDP；窄查詢的傳輸量隨詞彙而異，上方以 `/?query=公園` 與 `/?query=青梅生態池2號` 為準。
- 模擬的 Slow 4G 與 CPU 降速只是近似，不等於實機；實機行為需另外檢查。

### 競態修正

`e2e/district-filter.spec.ts` 的「選項筆數與結果一致」曾在完整關卡中失敗一次。原因是測試輔助函式 `total()` 在改選縣市後立即讀範圍文字，而範圍文字依設計會先經過「載入中」（尚未載入列表資料）才變成「共 N 筆」，讀到過渡文字就丟出例外，`expect.poll` 不會重試。網站行為沒有問題，修正在測試：讀不到「共 N 筆」時回傳 NaN 讓輪詢重試；另一處在帶條件進站後先輪詢到筆數少於全部，因為靜態第 1 頁的範圍文字也符合期待格式。修正前 `--repeat-each=30 --workers=8` 重現一次，修正後 80 次、720 個案例全數通過；整個套件加 `--repeat-each=3` 與 `--repeat-each=4 --workers=10` 沒有再出現間歇失敗。
