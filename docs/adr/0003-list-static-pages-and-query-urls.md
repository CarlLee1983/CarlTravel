# 景點列表用兩套網址：靜態的 `/page/N/` 與帶查詢參數的 `/?…`

景點列表每頁 24 筆。沒有任何條件時，第 1 頁是 `/`，第 N 頁是建置時預先產生的 `/page/N/`（N ≥ 2，不產生 `/page/1/`），分頁頁不進 sitemap。有任何條件（`query`、`county`、`kind`、`setting`、`age`）時，網址留在 `/`，以 `/?county=…&page=N` 表示，由瀏覽器依建置時產生的列表 JSON 與 Pagefind 命中渲染。換頁用 `pushState`，改條件與修正網址用 `replaceState`，改任何條件都回到第 1 頁；在 `/page/N/` 上套用條件時，直接導向 `/?…`。

會有兩套網址，是因為三個限制同時存在。靜態頁在請求時沒有程式碼可以執行，讀不到查詢參數，所以 `/?page=2` 與 `/` 是同一份 HTML，不能靠參數預先產生不同頁。篩選條件的組合無法預先產生：文字查詢的內容沒有上限，單看縣市、類型、環境、年齡帶四個選單，組合就有上千種〔推論，依選項數粗估，未實際產生〕，行政區加入後再乘上數百種，每種組合還要乘頁數，輸出檔案數會逼近 Workers 免費方案 20,000 檔的上限（CI 以 18,000 為界）。而沒有 JavaScript 的讀者仍然要翻得完全部景點，需要固定、可連結的路徑。所以無條件的分頁走靜態路徑，有條件的列表走前端渲染，無 JavaScript 時帶參數的網址只會看到未篩選的第 1 頁與「搜尋與篩選需要 JavaScript」。

不採用的選項有兩個。第一個是全部走查詢參數（`/?page=2`）：這樣只有一套網址，但無 JavaScript 的讀者翻不過第 1 頁，每一頁的分享連結也都要靠前端才有內容，所以不採用。第二個是預先產生所有條件組合：組合數與檔案數都爆炸，建置時間也跟著爆炸，且仍然無法涵蓋文字查詢，所以不採用。代價是同一份列表有兩種網址形式，且 `/page/N/` 與 `/?page=N` 的內容在沒有條件時等價，容易被人當成重複而「統一」掉；統一成任何一邊都會破壞上述其中一個限制。為降低混淆，`/?page=N` 在沒有任何條件時會導向 `/page/N/`。

這個決定可以回復：兩套網址共用同一個列表查詢模組與同一份卡片標記，移除靜態分頁或前端渲染任一邊都不需要遷移資料。

**Falsified if:** 頁面改由 Worker 或 SSR 在請求時渲染，靜態頁因此讀得到查詢參數，於是 `astro.config.mjs` 的 `output: "static"` 不再成立，`src/pages/page/[page].astro` 也不必預先產生，兩套網址可以合併成一套。
